# 公平性设计审查（规格书 17.1，验收 #52）

> 验收 #52：**不存在等级、永久装备、付费属性或外观稀有度带来的战斗优势。**
>
> 这一条是**设计审查**而不是代码功能 —— 它要求的是「某些东西不存在」。
> 所以本文档的写法是：逐条给出**判据**，并尽可能让判据能被机器复核，
> 而不是写一句「我们没有这些东西」。
>
> `pnpm verify:m9` 的 `#52` / `#52b` 会读这份文档并复核数据层。

**最后审查**：2026-07-30（M9）

> ⚠️ **复审已到期未做**（2026-08-09 登记）：§3 复审触发条件第 6 项「引入第一个
> 外部美术素材」已在 M12 发生（素材接入渲染与音频管线），而 §1.4 外观稀有度的
> 判据仍建立在「表现层全程序化、没有外部美术资产」的旧前提上。需要一轮正式
> 复审按有素材的前提重写 §1.4 并更新审查日期 —— 在那之前，本文档对 #52 的
> 论证在外观一节**不完整**。

## 1. 四项逐条对照

### 1.1 等级

**结论：不存在。**

| 判据 | 状态 |
|---|---|
| `ClassDef` 上没有 `level` / `xp` / `rank` 字段 | ✅ `verify:m9 #52b` 逐职业断言 |
| `CombatEntity` 上没有等级字段；生命上限直接来自 `ClassDef.baseHealth` | ✅ `sim/entity.ts` |
| 技能不按等级解锁：`ClassDef.skills` 是完整列表，开局全部可用 | ✅ `data/classes/*.ts` |
| 没有任何按时间/场次累积并影响战斗数值的持久量 | ✅ 无账号系统，见 §2 |

★ **同职业同装备的两名玩家，战斗数值完全相同。** 这不是靠自觉 ——
数值的唯一来源是 `ClassDef` + 当前武器/护甲的 `modifiers`
（M9 起真正生效，见 `sim/modifiers.ts`），没有第三个输入。

### 1.2 永久装备

**结论：不存在。装备是**战场内**临时资源。**

| 判据 | 状态 |
|---|---|
| 装备栏在**每局开始时**由 `createLoadout(classId)` 重建，只含职业默认装备 | ✅ `sim/loadout.ts` |
| 临时装备只能在战场内通过军械箱/掉落获得（10.1–10.5）| ✅ `sim/arsenal.ts` |
| 回合结束时 `resetLoadouts()` 清空全部临时装备（2.1 / 验收 #37）| ✅ |
| **死亡时**临时装备立即失效，不掉给敌人（10.10）| ✅ M9 补上接线，见 `sim/death.ts` |
| 默认装备不可删除、永不掉落，但也**没有任何强度优势** | ✅ 10.6 |
| 没有仓库、没有背包、没有跨局持久化的装备存储 | ✅ 全项目无此概念 |

★ 10.8 的五种护甲原型是**横向**取舍：每一件都同时有优势与代价。
`data.test.ts` 断言不存在全面上位装备（验收 #32），
`effects.test.ts` 另有两条断言它们在**数值上**真的有差异
（M9 之前这些 modifiers 是死数据，见 PROGRESS.md 的对应条目）。

### 1.3 付费属性

**结论：不存在。本项目没有账号系统、没有商店、没有任何支付路径。**

| 判据 | 状态 |
|---|---|
| 仓库内没有支付/订阅/内购相关代码或依赖 | ✅ `package.json` 依赖只有 three / ws / vite 工具链 |
| 没有账号、没有登录、没有玩家档案存储 | ✅ 房间以 `playerId` 字符串标识，仅存活于一局之内 |
| `localStorage` 只存**可访问性设置与键位**，不存任何影响战斗的量 | ✅ `settings/accessibility.ts` 的 `ACCESSIBILITY_STORAGE_KEY` 是唯一持久化键 |

★ 这一条目前是**天然满足**。若将来引入账号系统，本节必须重审 ——
那时判据从「不存在支付路径」变成「支付路径不接触战斗数值」，是完全不同的论证。

### 1.4 外观稀有度

**结论：不存在。外观与战斗数值在**类型层面**分离。**

| 判据 | 状态 |
|---|---|
| `WeaponDef` / `ArmorDef` 上没有 `rarity` / `quality` / `tier` 字段 | ✅ `data/schema.ts` |
| 外观只有 `appearance?: string`（一个材质/外观键），**不参与任何计算** | ✅ `verify:m9 #52b` 复核 |
| 13.2 / 验收 #10：所有人形职业共用同一套碰撞体，视觉大小不参与判定 | ✅ `GEOMETRY.HITBOX_RADIUS` 是唯一来源，`geometry.test.ts` 断言 |
| 表现层目前全程序化，没有外部美术资产，也就没有「稀有外观」这一概念 | ✅ docs/09 §7.1 |

★ **「外观不影响属性」在本项目里是结构性的**：
数值只从 `modifiers` 来（`sim/modifiers.ts` 的 `equipmentModifiersOf()` 只读
`WeaponDef.modifiers` / `ArmorDef.modifiers`），而 `appearance` 根本不在那条路径上。
想让外观影响属性，必须改 `equipmentModifiersOf` 的实现 —— 一次显眼的改动。

## 2. 17.1 其余三条的对照

17.1 一共四条，验收 #52 覆盖第一条（不出售战斗属性；外观品质 ≠ 装备强度）。
其余三条的落地位置一并记录，便于将来复审：

| 17.1 条款 | 实现处 | 验收 |
|---|---|---|
| 不出售战斗属性；外观品质 ≠ 装备强度 | 本文档 §1 | #52 |
| 临时装备必须横向取舍，不能同时提高伤害、攻速、防御、移动和控制 | `data/armors.ts` 的五种原型模板 + `data.test.ts` | #32 |
| 所有玩家使用相同目标规则、范围、碰撞体和镜头限制 | `constants/combat.ts`（`RANGE` / `GEOMETRY` / `CAMERA`）是唯一来源 | #9 / #10 |
| 同类控制、团队减伤、加速和治疗增益不能通过多职业重复无限叠加 | `sim/modifiers.ts` 的 `aggregateModifiers()`（减伤/减速/降治疗**取最强**）| #23 |

★ 最后一条在 M9 有一处需要特别记录的判断：**装备与光环分池聚合。**
8.4 / 17.1 的「取最强」防的是同类效果通过**多职业**重复叠加 ——
几个人往同一个目标身上堆效果。护甲只穿一件、由本人独占选择，结构上无法叠加，
所以装备池独立相乘。若把两者合池，任何一个减伤光环都会把护甲的减伤完全盖掉，
10.8 承诺的横向取舍会在最需要它的那几秒里消失。
`effects.test.ts` 有四条断言拦住这次重构。

## 3. 复审触发条件

以下任一项发生时，本文档必须重新审查并更新「最后审查」日期：

1. 引入账号系统、玩家档案或任何跨局持久化
2. 引入任何形式的支付、订阅、内购或激励视频
3. 给 `WeaponDef` / `ArmorDef` 增加 `rarity` / `quality` / `tier` 类字段
4. 让 `appearance` 进入 `equipmentModifiersOf()` 或任何数值计算路径
5. 给 `ClassDef` / `CombatEntity` 增加 `level` / `xp` / `rank` 类字段
6. 引入第一个外部美术素材（同时触发 docs/09 §7.1 的重启条件）

★ 第 3–5 项都是**加字段**，所以它们在 code review 里是可见的 ——
这就是为什么本文档的判据尽量写成「某个字段不存在」而不是「我们不会这么做」。
