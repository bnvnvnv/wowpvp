# M12 之后的路线图：让玩家进得来、玩得懂、留得下

> **背景**：M12（美术）与打击感改造完成后，项目所有者实测提出下一个问题：
> 「除了打击感，还有什么能引玩家？」本文是对这个问题的全盘回答与执行计划。
>
> **一条贯穿全文的判断**：这个游戏的核心卖点**已经做出来了** ——
> 反制链博弈（7.5 假读条骗打断、打断-学派锁定、陨石看倒计时走位）是
> 91 个技能、52 条验收堆出来的真深度。但目前玩家从「打开游戏」到
> 「感受到这个深度」之间，几乎每一环都是断的。
> 打击感解决的是「一击爽不爽」；本路线图解决的是「玩家能不能**玩到、
> 玩懂、玩下去**」。
>
> 与 [13-roadmap-post-m9.md](13-roadmap-post-m9.md) 相同：规格书之外的工程，
> 每个阶段自己定义完成判据，本文就是那份判据。

**创建**：2026-08-01（打击感改造完成后）

---

## 阶段总览

| 阶段 | 内容 | 完成判据 | 预估提交数 |
|---|---|---|---|
| **M13** | 对局入口：大厅 → 选职业 → 建/加房 → 准备 → 开局 | `verify:m13`：两个浏览器**纯 UI 操作**（零 URL 参数）完成一场对局 | 3–4 |
| **M14** | 数值配平：告别 19 处占位值 | `pnpm balance` 胜率极差 ≤ **30pp** 且无职业 <15% 或 >80%；每职业改动有记录 | 2–3 |
| **M15** | 新手引导：反制链任务式教学 | `verify:m15`：脚本走完全部教学环节；每环有「不教就过不去」的验证点 | 2–3 |
| **M16** | 对局完整性：战后仪式感 + 人机补位 + 消耗品 + 联网表现补齐 | ✅ **全部完成**（`verify:m16` 29/29）| 4–6 |
| **M17** | 留存钩子：生涯记录 → 外观 → 回放（**依赖对局人口，最后做**） | 方向性，届时再定判据 | — |

**顺序是有依赖的，不是偏好**：
- 入口必须最先做 —— 没有它，游戏**发不出去**（现状：联机要手写
  `?net=r1&team=blue&class=warrior` URL，见 `client/src/main.ts` 尾部）。
  后面所有验证「好不好玩」的工作都需要真人对局，而真人对局需要入口
- 配平在引导之前 —— 教学教人「职业各有反制」，而当前基线是猎人 95.2%
  胜率、战士 0%（`pnpm balance`，2026-08-01），先把地基找平再领人进门
- 留存钩子（段位/外观/回放）必须最后 —— 给空房间做装修没有意义

# M13 — 对局入口（投入产出比最高的一件事）

## 现状与目标

现状（`client/src/main.ts`）：默认进试验场；联机唯一入口是 URL 参数
`?net=<房间> &server= &team= &class= &name=`。协议与服务器侧**全部就绪**：
`RoomState` / `SelectTeam` / `SelectClass` / `SetReady` / `MatchStart` 消息、
房间生命周期、断线重连令牌（`server/room/reconnect.ts`）都在跑，
`NetworkScene` 构造时就是发这几条消息进房的（`NetworkScene.ts` 的 `joinRoom()`）。
**缺的只是 UI。**

目标：把链接发给朋友，他不需要任何说明就能进到同一场对局里。

## 交付物

1. **标题/大厅页**（DOM，不是 3D —— 与 HUD 同一套技术栈与 UI 缩放）：
   - 输入昵称、建房（生成短房间码）/ 按码加房
   - 房间内：成员列表（`RoomState.players` 直接渲染）、选阵营、准备状态
2. **选职业页**：8 个职业卡片 —— 模型预览（`ModelLibrary` 现成）、
   职业定位一句话、技能栏预览（`skillIconHtml()` 现成）。
   ★ 素材全部已有，这一页是纯组装
3. **单机入口并列**：「试验场（练习）」按钮 —— 试验场仍是默认路径的
   验收载体（141 项验收跑在上面，**不能变**），大厅通过 URL 无参路径进入它
4. **对局结束回房间**：`MatchEnd` 后回到房间页可再开一局（协议已支持）

## 红线

- ★ `?net=` / `?art=` 等既有 URL 参数**原样保留** —— 全部 verify 脚本靠它们
- ★ 大厅只发协议里已有的消息类型。需要新消息（如「房间列表」）就先加协议 +
  `codec` 校验 + `FORBIDDEN_CLIENT_FIELDS` 检查，照 M10 的规矩
- ★ 服务器仍校验一切（阵营人数、职业合法性）—— UI 只是发意图

## 判据（`scripts/verify-m13.mjs`，照 verify-m10 的双浏览器模式）

- 浏览器 A 纯点击：起服务器 → 建房 → 选职业 → 准备
- 浏览器 B 纯点击：按房间码加房 → 选另一阵营职业 → 准备 → 双方进入对局
- 对局里 A 打 B 一次，双方都收到 Damage（复用 m10 的判据函数）
- MatchEnd 后回到房间页，再开一局成功
- 全程 `location.search` 里没有 `net=`（证明不是 URL 老路）

# M14 — 数值配平

## 现状

PROGRESS「技术债 §2」：19 处伤害数值是占位值且当初没写推导来源。
`pnpm balance`（168 场，种子=1，确定性可复现）2026-08-01 基线：

```
hunter 95.2% · rogue 88.1% · deathknight 66.7% · mage 57.1%
priest 42.9% · paladin 28.6% · druid 21.4% · warrior 0.0%
极差 95.2pp。暴击（偏差 #7）已含在此基线内（均值 +5%）。
```

## 做法约束（写给执行者）

- ★ **bot 基线是回归工具不是平衡真相** —— AI 不会假读条、不会留打断、
  不会绕柱（balance-report 自己的输出注释就这么写）。用它看「改一个数值
  谁动了多少」，别照胜率直接拉平
- ★ 先修**离群**再修中间：hunter 2.7 秒平均对局（秒杀）与 warrior 0%
  （无伤害输出路径？先查是不是 bot 不会用怒气）大概率是 bug 级问题，
  不是调 5% 能解决的 —— 每一项先诊断根因再动数值
- ★ 每处改动在 `data/classes/*.ts` 的数值旁写一行为什么（技术债 §2 的教训：
  19 处占位值的由来在代码里完全找不到）
- ★ 动任何 shared/sim 数值后重跑 `pnpm balance` 并把新基线写进提交信息

## 判据

- `pnpm balance` 极差 ≤ 30pp；无职业 <15% 或 >80%；无平均对局 <6 秒
- 单测全绿（配平只动数值不动规则 —— 若某条规则测试红了，说明改错了层）
- docs/10 技术债 §2 标记为已处理，各职业改动清单入 PROGRESS

# M15 — 新手引导（反制链任务式教学）

## 为什么值得单独一个里程碑

本作最有味道的机制**不教就感受不到**。试验场的三个假人本来就是照
反制链设计的（`CombatDirector.ts` 注释原话：「三个假人，各自演示反制链
的一环」：战士会拳击打断你、法师读条打你、牧师奶战士）——
教学的**载体已经全在**，缺的是任务脚本与提示 UI。

## 交付物（一串递进任务，完成一环亮下一环）

1. 基础：移动/镜头/选中/放一个技能（现有 HUD 提示升级为任务打勾）
2. **打断**：法师读条时用拳击打断它 → 观察学派锁定图标
3. **被打断的代价**：故意被战士拳击 → 冰系锁 4 秒，切火球
4. **假读条**（7.5，本作灵魂）：起手读条 → 立刻 Esc → 战士的拳击落空 →
   任务提示「他的打断进冷却了，这 10 秒他拿你没办法」
5. **走位反制**：站进陨石落点圈 → 看倒计时数字走出去（14.3 的倒计时
   就是为这一刻做的）
6. 毕业：一场против三假人的完整小胜（血量调低的速胜局）

## 红线与判据

- ★ 教学状态存 localStorage（照 `accessibility` 的持久化模式），
  可跳过、可重进；**不动 sim 一行** —— 任务判定全部读现有事件流
  （`onCombatEvent` / `onCastActivity`，与统计同为纯折叠）
- `verify:m15`：Playwright 按任务顺序操作，断言每环「不做对就不通过」
  （例如假读条环：不按 Esc 直接读完 → 任务不亮）

## 16b 人机补位（小体量联机游戏的保命项）

- ⚠️ **本条原先的前提是错的，已更正。** 原文写「`ArenaDirector` 已能脚本 AI
  打整场（现用于观战演示）」—— 核实后：那个类**没有任何 AI 决策**（无施法、
  无移动）、**不调 `tickWorld`**（自己手写了第二份 tick 顺序，且 `tickAuras`
  的返回值被 `void t` 丢弃 → DoT/HoT 在那里根本不结算）、**全仓库零 import**。
  它是死代码，**已于本轮删除**。按原计划「把它那套 AI 搬到服务器」会发现
  没有东西可搬。
- ✅ **决策层已提取**：真正能打整场的是 `scripts/balance-report.ts` 的 `think()`
  （168 场确定性对局实证、全程走 `inputs` + `castRequests` 公共通道、唯一会移动），
  现已提成 `packages/shared/src/ai/botController.ts`，试验场「实战模式」（按 K）
  已经在用。提取后 `pnpm balance` 基线逐位不变（28.6pp / 33.3–61.9%）。
- ✅ **服务器侧接管已交付**，走的正是当初探明的那条路：
  `BotSocket`（假 socket，三个成员）+ **真的 `Session`** + `MatchLoopDeps.onPreTick`。
  人机每 tick 发的是真的 `Input` / `CastRequest` **JSON**，经过
  `handleRaw → parseClientMessage（形状+范围）→ 阶段鉴权 → 排队 → tickWorld`
  —— 与真人**一模一样的入口**。
  ★★ 于是「人机不发 `FORBIDDEN_CLIENT_FIELDS`」不是靠我们记得别发，
  而是 codec 会把它拒掉；「人机能做真人做不到的事」在结构上写不出来。
  ⚠️ 更省事的写法是直接往 `MatchLoop` 的 inputs Map 里塞 —— 能work，
  但那等于开第二条输入通道，回放与反作弊边界都从那里破掉。
- ✅ **人数不足填充人机**：`RoomConfig.fillWithBots`（房主可改，**默认关**）。
  ★ 默认关不是保守：打开会改变**开局时世界里有几个实体**，
  而两百多项验收全部建立在「场上就这么几个人」这个初始条件上
  （与试验场实战模式默认关是同一条教训）。
  人机是**真正的房间成员**（走 `joinRoom`/`selectSlot`/`selectClass`/`setReady`），
  所以阵营上限、职业合法性、`canStart()` 照常约束它们，无需到处加
  「如果是人机则…」的分支。
- ✅ **规格冲突已拍板**（2026-08-04，登记为 docs/10 已知偏差 #14）：
  取**断线瞬间接管、重连交还、整局内令牌有效**。于是 11.5 的「留在原地被打」
  与「超时淘汰」两条都不再发生 —— 规格书本体不改，偏差表登记。
  ★ 不构成「用断线洗战绩」的后门：接管的是**同一个实体**，照常被打、照常会死、
  统计照常记在这个玩家名下；**主动退出（`LeaveMatch`）仍然立即淘汰**。
  ★ 接管写在**调用方**（`MatchLoop`），`reconnect.ts` 继续只产出名单 ——
  让它拿到 World 会同时打穿「断线不给无敌」那条（它正是靠依赖缺失表达的）。
- ★ 红线：人机走与真人完全相同的输入通道（发 Input 消息进 tickWorld），
  **不允许**直接改 world —— 否则回放与反作弊边界全破
- 判据：verify 脚本单人 + 3 人机打完一整场；人机不发任何
  `FORBIDDEN_CLIENT_FIELDS` 字段（自动满足，因为走 codec）
