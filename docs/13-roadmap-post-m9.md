# M10 — 联网对战

## 0. 两个必须先定下来的判断

### ★★ 判断一：把 tick 顺序放进 `shared`，而不是在服务器再写一遍

docs/02 §3 定义了九步 tick 顺序，并明确「**顺序不能随意调整**」。
现在这个顺序**只存在于 `client/src/combat/CombatDirector.ts` 的 `update()` 里**，
而且是隐式的 —— 靠一串函数调用的书写次序表达。

如果服务器再写一份，就有了两个实现。而本项目已经**四次**遇到
「规则写对了、单测全绿、但没人调用它」（M3/M4 的七个、M8 的 #2、M9 的两个）——
两份 tick 顺序会制造这类 bug 的第五个变种，而且是最难查的那种：
两边都能跑，但结算次序差一步，于是同一发技能在客户端预测里命中、在服务器判定里落空。

**做法**：新增 `shared/src/sim/tick.ts`，把九步顺序写成**一个函数**：

```ts
export const tickWorld = (deps: TickDeps, dt: number): TickResult
```

服务器与客户端本地模拟都调它。★ 顺序因此只有一处定义，
而 M9 新增的那条约束（`settleDeaths()` 必须在 `tickSwaps()`/`tickPickups()` **之后**）
也只需在一处保证。

**代价**：`CombatDirector` 要改造成 `tickWorld` 的调用方。这是一次真实的重构风险，
所以放在 M10 的第二步（A2）单独做、单独验，不和网络代码混在一个提交里。

### ★★ 判断二：**不改试验场**，另加一个联网场景

`TestbedScene` 是 M1–M8 共 **106 项**端到端验收的载体。
把它改造成「从服务器收快照」会同时打掉这 106 项 —— 而它们目前是全绿的。

**做法**：新增 `client/src/scenes/NetworkScene.ts`，与试验场并存：

| 场景 | 数据来源 | 用途 |
|---|---|---|
| `TestbedScene` | 本地 `tickWorld` | M1–M9 验收载体，**保持可用** |
| `NetworkScene` | 服务器快照 | M10 的验收载体 |

两者共用 render / camera / hud / vfx / settings 全部表现层代码 ——
差别只在「世界状态从哪来」。★ 这也顺便验证了一件事：
如果表现层能同时吃本地模拟和远端快照，说明它确实没有偷偷依赖模拟内部状态。

## A1. 协议定义与编解码分离

**文件**
- `shared/src/net/protocol.ts` —— `ClientMessage` / `ServerMessage` 的**类型定义**
- `shared/src/net/codec.ts` —— JSON 编解码 + **入站校验**
- `shared/src/net/protocol.test.ts`

**依据**：docs/08 §3 已经把两个联合类型草拟好了，照抄落地，不另发明。
docs/08 §7 要求「消息定义」与「编解码」分成两个文件，为将来换二进制留路径 —— 照办。

**★ 结构性保证：客户端发不出「结果」**

docs/08 §2：「客户端**永远不发送**『我造成了 X 伤害』这类结果，只发送意图。」
这是一条否定式规则。做法：

1. `ClientMessage` 联合里只有意图消息（`Input` / `CastRequest` / `SetTarget` / …）
2. 配一条测试，遍历 `ClientMessage` 的全部成员，断言没有任何成员带
   `damage` / `amount` / `health` / `kills` / `hit` 这类结果字段名 ——
   加一个就会红

**★ 入站校验是安全边界，不是防御性编程**

`parseClientMessage(raw: unknown)` 必须在消息碰到 sim 之前把它验完：
消息来自**不受信任的**浏览器，可以是任意 JSON。
返回 `{ ok: true; msg } | { ok: false; reason }`，**不抛异常** ——
一个畸形包不该让整个房间掉线。

需要校验的不只是形状，还有**范围**：`move.forward` 必须在 [-1, 1]
（不然客户端发 999 就能加速），`dt` 必须在合理区间（不然发 dt=100 就能瞬移）。
★ 这两条是真实的作弊向量，`verify:m10` 会各试一次。

**完成判据**：编解码往返测试；作弊字段测试；越界输入被拒绝。

## A2. 把 tick 顺序收敛进 `shared/src/sim/tick.ts`

**文件**
- `shared/src/sim/tick.ts`（新）
- `shared/src/sim/tick.test.ts`（新）
- `client/src/combat/CombatDirector.ts`（改造为调用方）

**内容**：把 docs/02 §3 的九步写成一个函数，`TickDeps` 收全部 store。
返回 `TickResult`（本 tick 的全部事件），供统计折叠、HUD 播特效、快照广播消费。

**★ 顺序约束要写成可测的**，不只是注释。做法：
`tick.test.ts` 构造几个「顺序反了就会错」的场景各断言一次：

| 场景 | 顺序反了的后果 |
|---|---|
| 原地读条 + 本 tick 移动 | casting 在 movement 之前 → 移动打断慢一个 tick（7.3）|
| 同 tick 死亡 + 换装完成 | settleDeaths 在 tickSwaps 之前 → 吃掉 `result:'death'` 事件（17.3）|
| 本 tick 新加的控制 | deriveStatusFlags 不在最后 → 控制要等下一 tick 才生效 |
| 死亡 + 胜负判定 | matchRules 在 deaths 之前 → 胜负慢一个 tick |

**风险**：这是唯一一步会动到已通过验收的代码。
**缓解**：改完立刻跑全部九个 verify 脚本，任何一项掉了就地修，不往后带。

**完成判据**：`tick.test.ts` 四条顺序断言 + M1–M9 全量回归不掉项。

## A3. 服务器：房间会话与 MatchLoop

**文件**
- `server/src/room/Session.ts` —— 一个 WebSocket 连接的生命周期
- `server/src/room/RoomServer.ts` —— 房间集合、加入/选职业/准备/开局
- `server/src/MatchLoop.ts` —— 20Hz 定步长循环
- `server/src/index.ts` —— 从 M0 的连通性桩改成真服务器

**关键点**
- 房间**规则**复用 `shared/src/sim/match/room.ts`（3.2 自由阵容那套），服务器只做传输
- 断线复用 M9 的 `reconnect.ts`。★ 超时淘汰的**后果**在 MatchLoop 里执行 ——
  `takeExpired()` 只给名单，这是 M9 刻意留的设计
- 20Hz 用累加器补帧，不用 `setInterval` 直接跑 —— 否则事件循环抖动会让
  模拟时间漂移，而 8.2 的递减窗口、12.6 的复活波次都是绝对时间

**★ 一处容易写错的**：`MatchLoop` 每 tick 要为**每个客户端**单独建快照
（`buildSnapshot(deps, viewer)`）。12v12 是 24 份。
不要为了省一次遍历先建一份全量再裁 —— M9 的 `visibility.ts` 刻意没提供那个入口，
理由写在那个文件头部。

**完成判据**：两个真实 WebSocket 客户端能加入同一房间、开局、收到快照。

## A5. 客户端网络层：预测、纠正、插值

**文件**
- `client/src/net/Connection.ts` —— WebSocket 与重连
- `client/src/net/Predictor.ts` —— docs/08 §5 的七步
- `client/src/net/Interpolator.ts` —— 其他玩家的 100ms 延迟缓冲
- `client/src/scenes/NetworkScene.ts` —— 联网场景（见判断二）

**docs/08 §5 的七步照实现**，其中第 6 步「用同一份 `shared/sim/movement` 重放」
是整个设计成立的前提。

**★ 13.4 的硬要求**：「传送、位置纠正和大位移不能被识别为高速跑步。」
所以插值器必须检测大跳变并**直接瞬移而非插值** ——
否则一次纠正会让远端角色以 40 米/秒的速度滑过去，动画状态机会判成冲刺。
`MovementState.teleported` 已经有这个标志（M1 就留了），快照里要带上它。

**完成判据**：
- 预测与纠正：模拟 150ms 延迟，本地移动无卡顿，纠正后位置收敛
- 插值：远端角色移动平滑，一次 5 米的纠正**不触发**跑步动画

## A6. `verify:m10` 端到端验收

**文件**：`scripts/verify-m10.ts`

★ 与前九个脚本的分工：这一支要跑**真实的两端** —— 起一个真服务器进程，
连两个真 WebSocket 客户端。前九支验的是「规则对不对」和「有没有接线」，
这一支验的是「**跨进程之后还对不对**」。

必验项（每一条都是「试着做坏事然后断言失败」）：

| # | 内容 | 为什么必须端到端 |
|---|---|---|
| 1 | 未被发现的潜行者**不出现在传输字节里** | 客户端过滤和快照裁剪在单进程里看不出区别 |
| 2 | 敌人的备用装备不出现在传输字节里（#36）| 同上 |
| 3 | 敌方技能冷却不出现在传输字节里 | 同上 |
| 4 | 客户端伪造 `move.forward = 999` → 被钳制，不加速 | 越界校验只有真的发一次才知道有没有生效 |
| 5 | 客户端伪造 `dt = 100` → 被拒绝，不瞬移 | 同上 |
| 6 | 客户端伪造一条不在协议里的消息 → 被拒绝且**不掉线** | 畸形包不该拖垮房间 |
| 7 | 客户端对不可见目标发 `SetTarget` → 被拒绝 | 服务器要校验目标在该客户端的可见集合里 |
| 8 | 断线 90 秒内重连 → 收到完整快照并恢复控制 | 跨进程的状态恢复 |
| 9 | 断线期间角色照样掉血（11.5）| 否定式规则，必须真的打他一下 |
| 10 | 断线超时 → 按淘汰处理 | |
| 11 | 两个客户端看到的**同一个事实**一致（比分、旗帜状态）| 权威性 |
| 12 | 一局 3v3 从房间到分出胜负跑完 | 集成 |

**完成判据**：12 项全绿，且 M1–M9 的 141 项不掉。

1. **`assets/` 目录与登记表校验机制** —— `verify:m12` 建议断言：
   - `assets/` 下每个包前缀在 docs/09 §4 有登记（GH / T2 / T3）
   - `T1` 路径必须在 `assets/local/`（gitignore）
   - 无暴雪资源启发式扫描（可选）

   引入真实模型时这条要重新验一遍

## ★ 引入美术时会被挑战的两条既有保证

| 保证 | 引入素材后的风险 | **重验结果** |
|---|---|---|
| 验收 #10「模型大小不改变碰撞体」| 真实模型的视觉体型各不相同，必须确认碰撞体仍统一取 `GEOMETRY.HITBOX_RADIUS` | ✅ `verify:m12` #10-m12：模型在 `ModelLibrary` 里按包围盒归一化到 `HITBOX_HEIGHT`，实测各职业偏差 < 0.01 m |
| 验收 #48「低画质不隐藏关键信息」| 贴图与粒子在低画质下往往整体关闭，容易连关键信息一起关掉。M8 的 `hiddenAtQuality(role: DecorativeRole)` 保证必须继续成立 | ✅ `verify:m12` #48a/b/c：最低画质卸掉 IBL（14.4 允许的「非关键光照」，走的正是 `isVisible('ambientLight', tier)`），角色模型与 HUD 五块一块不少 |

这两条都要在 `verify:m12` 里重验，而不是假定 M1/M8 的结论自动延续。

> ★★ **重验第一次跑就抓到了东西 —— 但不是产品缺陷，是检测本身错了。**
> `#10-m12` 报某个模型身高 1.987 而非 2.000，查下来是**量错了对象**：
> 包围盒把挂在骨骼上的长杖和当前动画姿势一起量了进去
> （牧师假人实测在 1.976～2.149 之间摆动）。
> 这正好说明为什么「重验」不能省 —— 顺手写一条检测然后看它变绿，
> 和真的知道自己在测什么，是两件事。
