# 技术架构设计

> 设计文档明确**不规定**编程语言、框架、网络架构、数据库或代码目录（1.2）。
> 因此本文是工程侧的自主决策，但每一条决策都要能回答「它如何保障规格书里的某条规则」。

## 0. 技术选型与理由

| 选择 | 理由 |
|---|---|
| **TypeScript** | 附录A#3/#4 要求每个技能/武器必须标注一组固定属性。把它做成必填字段，编译器就成了执行这条约束的人，而不是靠 review。 |
| **three.js** | 需求是「自由镜头 + 风格化低模 + 技能特效分层」，不需要完整引擎的编辑器与物理。three.js 的控制粒度正好匹配 4.x 镜头规则和 13.x 移动物理要求。 |
| **原生 WebSocket（`ws`）+ 自研权威 tick** | 6.x 的距离/视线/朝向、7.x 的施法打断、10.x 的换装争夺都需要精确的服务器裁决。成熟同步框架的状态抽象反而会挡路。 |
| **pnpm workspace** | 三个包共享 `shared`，`shared` 必须能同时跑在浏览器和 Node 里。 |
| **vitest** | `shared` 是纯函数与纯状态机，天然可单测。52 条验收标准里大部分能写成断言。 |

### 为什么 `shared` 必须零依赖

**验收 #8 要求「地面技能真实范围边界与实际判定一致」。**
唯一能保证这件事的方法，是让客户端画指示器和服务器做判定**调用同一个函数**。
所以所有几何判定都在 `shared/math/geometry.ts`，客户端不允许自己实现任何命中逻辑。

同理，`shared/sim` 里的施法状态机、控制递减、光环聚合，服务器用它做权威结算，
客户端用它做本地预测 —— 同一份代码，不存在「客户端以为能放、服务器说不能」的分歧来源。

## 3. 核心数据流

### 一次技能释放（对应 7.4 施法生命周期）

```
客户端                          服务器
  │
  │ 1 按下技能键
  │   本地预检（casting.canCast）—— 立刻给玩家「超距/无视线/朝向错误」反馈
  │   预检不通过 → 只播放失败提示，不发包
  │
  ├─ CastRequest{skillId, targetId?, groundPoint?, facing} ──►
  │                                    2 服务器重新做同一份预检
  │                                      （权威；客户端预检只是延迟优化）
  │                                    3 开始施法：写入 CastState，启动 GCD
  │◄─ CastStarted{casterId, skillId, duration, interruptible, school} ─┤
  │   显示施法条（含盾牌标记）
  │
  │                                    4 每 tick 检查：移动 / 控制 / 强制位移 / 打断
  │◄─ CastInterrupted{source, schoolLock?} ─────────────────┤（若被打断）
  │
  │                                    5 完成瞬间**再次**检查目标存活/距离/视线/朝向/落点合法
  │                                      不合法 → 失败，不扣资源不进冷却（7.4#6）
  │◄─ CastCompleted / CastFailed{reason} ───────────────────┤
  │                                    6 成功：扣资源、进冷却、结算效果
  │◄─ Snapshot（伤害、光环、位移…）─────────────────────────┤
```

**关键：第 2 步和第 5 步必须调用完全相同的检查函数**（`casting.validate`），
否则会出现「开始能放，完成时莫名失败」或反过来的不一致。验收 #19 直接考这一点。

### 一次 tick（服务器，20Hz）

```
applyInputs        应用本 tick 收到的移动/朝向/技能请求
  ↓
movement           13.5 物理：滑墙、跨障、坡度、跳跃动量、位移技能落点钳制
  ↓
casting            推进施法条/引导/射击准备，检查中断条件
  ↓
auras              周期跳、持续时间递减、受伤解除、护盾衰减
  ↓
projectiles        碰撞投射物推进与命中；锁定投射物到期结算
  ↓
groundAreas        地面区域周期结算、延迟落点触发、陷阱触发
  ↓
matchRules         回合状态、战斗抑制、旗帜状态机、复活波次、聚焦叠层
  ↓
deaths             死亡结算、存活人数（宠物不计入）、平局判定
  ↓
snapshot           视野裁剪后广播（未被发现的潜行目标不进快照）
```

**顺序不能随意调整**。例如 `casting` 必须在 `movement` 之后 ——
7.3 规定「主动移动停止标记为原地施放的读条」，只有先算完移动才知道这一 tick 有没有位移。

## 4. 效果注册表：扩展性的核心

新增一个技能机制，**不修改任何已有代码**，只做两件事：

1. 在 `schema.ts` 的 `EffectDef` 联合类型里加一个成员
2. 在 `sim/effects/index.ts` 注册一个处理器

```ts
// sim/effects/index.ts
export type EffectHandler<K extends EffectDef['kind']> = (
  ctx: EffectContext,
  effect: Extract<EffectDef, { kind: K }>,
  targets: readonly EntityId[],
) => void;

const handlers = new Map<EffectDef['kind'], EffectHandler<never>>();
export const registerEffect = <K extends EffectDef['kind']>(kind: K, h: EffectHandler<K>) => { … };
```

`EffectDef` 是可辨识联合，所以**漏注册一个 kind 会编译报错**，不会静默失效。

对于确实无法数据化的一次性机制（例如德鲁伊野性冲锋按形态分支），
用 `{ kind: 'custom', handler: '…' }` 逃生舱，但**必须在代码注释里写明为什么不能数据化**。
逃生舱用得越多，说明 schema 抽象得越差 —— 定期回头把重复出现的 custom 提炼成正式 kind。

## 5. 权威与预测

| 谁决定 | 内容 |
|---|---|
| **仅服务器** | 伤害、治疗、命中与否、控制生效、拾取归属、旗帜状态、死亡、存活人数 |
| **客户端预测，服务器纠正** | 自己的移动与朝向 |
| **仅客户端** | 镜头、特效、音效、HUD 布局、画质档位 |

**断线不提供无敌**（17.3）：角色留在原地、可被攻击，服务器继续模拟。
重连后恢复「服务器认可的唯一状态」，客户端本地预测状态一律丢弃。

**视野裁剪是安全边界，不是优化**：
未被发现的潜行目标**根本不进快照**（5.3 / 验收 #5）。
如果只在客户端隐藏，改一行前端代码就能作弊。同理，敌人的**备用装备不进快照**（10.6 / 验收 #36）。

## 6. 地图表示

首版用**轴对齐包围盒（AABB）组合**描述地形，不引入网格碰撞或物理引擎。

```ts
interface Aabb {
  min: Vec3; max: Vec3;
  blocksSight?: boolean;    // 6.4：低矮栏杆设 false，只挡移动不挡视线
  blocksMovement?: boolean;
}
```

理由：
- 6.4 明确区分「阻挡视线」和「只挡脚部」，AABB 加一个 flag 就能表达，网格碰撞反而难以标注
- 竞技场地图是柱子、墙、拱门的组合，AABB 天然贴合
- 判定极快且完全确定，服务器与客户端结果逐位一致

代价：不支持斜面墙和曲面。M5 做地图时若确实需要，再引入凸多面体，
但**必须同时更新 `geometry.ts`，不能让客户端和服务器用不同的碰撞表示**。

## 7. 加一个东西要改哪些文件

详见 [11-contributing.md](11-contributing.md)，这里给速查：

| 要加什么 | 改哪里 | 是否需要动引擎 |
|---|---|---|
| 一个技能 | 对应 `data/classes/<职业>.ts` 加一个 `SkillDef` | 否（若用现有 EffectDef kind） |
| 一个职业 | 新建 `data/classes/<新职业>.ts` + 在 `data/index.ts` 注册 | 否 |
| 一件武器/护甲 | 对应职业文件的 `weapons` / `armors` 数组 | 否 |
| 一种全新机制 | `schema.ts` 加 `EffectDef` 成员 + `sim/effects/` 注册处理器 | 是，但只加不改 |
| 一张地图 | 新建 `data/maps/<地图>.ts` | 否 |
| 一种视觉表现 | `client/src/vfx/` 注册表 | 否 |
