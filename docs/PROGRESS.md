## 清账批次一 · A1：LeaveMatch 淘汰接进死亡漏斗（2026-08-04）

docs/16 批次一第 1 项，技术债总账 A1 清偿。

### 根因：注释与实现相反

`RoomServer.eliminate()` 的注释声称在执行 11.5「主动退出不能规避死亡统计」，
实现却是直改 `e.alive / e.health` —— 不产生 `death` 事件，于是三件事**静默不发生**：

- 统计不记 deaths（**恰好违反注释引用的那条 11.5**）
- `settleDeaths()` 不跑 —— 10.10 临时装备不清（夺旗波次复活会滚雪球的那条）
- 客户端收不到 `Death` —— 对手看到人凭空躺下，击杀播报/死亡回顾全缺席

「规则写对了、没人调用」家族的又一员：死亡漏斗每一环都是对的，
弃权这条路**绕开了整条漏斗**。2026-08-04 全仓审计（服务器公平性路）发现。

### 修法：弃权成为 tick 的第 0 步

- `TickDeps.forfeits?: ReadonlySet<EntityId>` —— tick 第 0 步用与 `dealDamage()`
  **完全相同**的死亡表达（`alive=false` + `death` 事件 + `onEffects`），
  于是统计折叠（第 9 步）、胜负判定（第 10 步）、settleDeaths（第 11 步）、
  服务器的 Death 广播全部自动跟上，不需要谁记得
- `MatchLoop.forfeit(playerId)` 只排意图 —— 与施法、消耗品同规矩：
  **结算只有 tickWorld 一个出口**（A2 的老教训）
- `eliminate()` 改为 `sr.loop?.forfeit(playerId)`；killerId **如实缺席**
  （弃权没有凶手，编一个会让击杀播报冤枉人 —— M16a「如实，不编」同则）
- 超时淘汰共用同一条路（当前因 24h 宽限不触发，偏差 #14）
- 时序不变：旧写法改字段后也要等下一 tick 的 `tickArena` 判胜负，
  新写法在同一个 tick 的第 0 步判死、第 10 步判胜负 —— 玩家感知零差异

### 验证

typecheck ✓ · **1114 单测**（+1）· `verify:m10` 15/15 · `verify:m16` 29/29 ·
`pnpm balance` 基线**逐位不变**（28.6pp；决斗不走弃权路径，第 0 步对无
`forfeits` 的调用方是空转）·
**变异测试**：把第 0 步改回「只改字段、不发事件」，新断言红、其余 13 条不动。

新断言（`RoomServer.test.ts`，真 socket）三条各对一个洞：
对手收到 `Death` 且无 killerId、临时装备清空 + 回落默认武器、
结算面板（`MatchStats`）里退出者 deaths = 1。

## 清账批次一 · A6：跨房间重连不再泄漏房间（2026-08-04）

## 清账批次一 · A3：心跳让半开连接真的触发接管（2026-08-04）

docs/16 批次一第 3 项，技术债总账 A3 清偿。

**根因**：服务器没有任何 ping/pong 或空闲检测。半开连接（断电、拔网线、
NAT 超时）不触发 `'close'` —— 偏差 #14 承诺的「断线瞬间接管」只对**优雅关闭**
的连接成立，最常见的断线形态下那个角色是一具站着挨打的尸体，
直到 TCP 自己超时（可能十几分钟）。

**修法**：`startServer` 加心跳（可配置，默认 30s ping、连续 2 次无 pong 判半开）。
pong 由对端 ws 实现按 RFC 6455 自动回复，不需要客户端代码配合；
落空达到上限 → `terminate()` —— 它触发的是与正常断线**同一个**
`'close'` → `disconnect()` → `takeOverByBot()` 路径，**不开第二条断线通道**
（与 BotSocket 不开第二条输入通道同一条纪律）。

**验证**：typecheck ✓ · **1117 单测**（+1）· `verify:m10` 15/15 ·
新断言（真 socket）：暂停蓝方底层 TCP 读取模拟半开 —— 对手收到
`PeerDisconnected`、角色仍在世界里且活着（接管的是同一具身体）·
**变异测试**：拿掉 terminate，断言在超时上红。

## M16b：人机补位与掉线接管（2026-08-04）

docs/14 §16b + 已知偏差 #14（用户拍板：**断线瞬间接管、重连交还、
整局内令牌一直有效**）。

### ★★ 红线是「人机走与真人完全相同的输入通道」—— 字面兑现

一个人机 = **一个假 socket（`BotSocket`，三个成员）+ 一个真的 `Session`**。
它每 tick 发出的是真的 `Input` / `CastRequest` **JSON 字符串**，经过：

```
handleRaw → parseClientMessage（形状 + 范围校验）→ 阶段鉴权 → 排队
          → MatchLoop 按 tick 消费 → tickWorld
```

于是 docs/14 的判据「人机不发任何 `FORBIDDEN_CLIENT_FIELDS`（自动满足，
因为走 codec）」**真的**自动满足 —— 不是靠我们记得别发，是 codec 会拒掉。

⚠️ 更省事的写法是直接往 `MatchLoop` 的 inputs Map 里塞。能work，
但那等于开第二条输入通道，回放与反作弊边界都从那里破掉。
**多写一个假 socket，换掉一整类将来才会发现的问题。**

★ 决策层没有重写：用的还是 `shared/src/ai/botController.ts` 的
`decideBotAction()`（168 场确定性对局实证过的那一个，试验场实战模式同款）。
本轮只加了「把它的产出翻成协议消息」这一层。

### 接管与交还

| 时刻 | 动作 |
|---|---|
| 断线 | `takeOverByBot()` —— 用**同一个 playerId** 建一条假会话。于是在 `collectInputs()` 眼里它与真人同构（同一个 `entityOf.get(s.playerId)`、同一套 codec）|
| 重连 | `handBackFromBot()` —— 先从 `sessions` 摘掉假会话再登记。★ 顺序要紧：反过来的话两条会话会在同一 tick 为同一实体各投一份输入，而 `collectInputs()` 取「最后一条」，人的操作会被人机盖掉（那种 bug 的表现是「角色偶尔不听使唤」，极难查）|
| 超时 | **不再发生**。★ 表达方式是把宽限期放到长于任何一局（`TAKEOVER_GRACE_SECONDS`），于是 `takeExpired()` 永远返回空 —— `reconnect.ts` **一行没改**，因为它只做判定，阈值本来就该由调用方给 |

★ `settleExpiredReconnects()` 那条链路**刻意保留**：它同时是 11.5
「主动退出不能规避死亡统计」的执行点，那条规则没有被改。

### 人机补位

`RoomConfig.fillWithBots`（房主可改，**默认关**）。

### 三处「如实，不编」

1. **`killerId` 可空**是协议的事实（验收 #5：被看不见的人打死时来源被抹掉）——
   播报如实写「阵亡」。编一个凶手会让玩家去报复一个没打过他的人。
2. **死亡回顾显示学派不是技能名** —— 协议的 `Damage` 只带 `school`。
   要真名得给协议加 skillId，那是独立的一笔债，**记在注释里，不假装已解决**。
3. **`ui_arena_win` 在素材盘里不存在**（只有 `ui_arena_loss`）——
   胜利用 `ui_achievement` 顶上。写一个不存在的资源 id 会是**静默的加载失败**：
   没有声音，也没有报错。

### 写脚本时踩到的三个坑（都留在注释里）

1. **准备阶段有 18 秒** —— 在那期间打死人不会结束对局。第一版靠真实时间打，
   蓝方死了却收不到 `MatchEnd`，报出来像「统计没下发」，真相是这局还没进战斗。
   改用 `loop.advance()` 单步快进（与 verify-m10 #12 同一手法）。
2. **死亡与复活可以在同一 tick 里发生** —— 从外面**永远观察不到**
   `alive === false` 这个中间态（settleDeaths → 回合判定 → 复活重置）。
   判据改成「客户端收到的 `Death` 消息」：消息流是外部可观测的事实，中间态不是。
3. **队列没冲完不等于没发生** —— 同步跑一千多个 tick 会往 socket 里塞
   两千多份快照，Damage/Death 排在后面还没送到。固定 `sleep(200)` 读到空列表，
   报「收到 Death 0 条」。改用 `waitFor`。

### 池预算（12v12 最坏情况）

发射器占用的并发槽 = `ceil(life / cadence)`，全部**算出来的不是调出来的**：

| 池 | 容量 | 占用 |
|---|---|---|
| 事件池（命中/释放/死亡/破盾/规避）| 32 格 × 48 粒 | 一发 8 目标 AOE = 8 主爆发 + 8 碎屑 = 16；两发重叠恰好打满 |
| 细流池（拖尾/地面填充/蓄力）| 48 格 × 32 粒 | 蓄力 4×3 + 拖尾 4×6 + 地面 3×4 = 48 |

中画质 density 0.5 → 节拍加倍 → 负载减半；低画质 density 0 → 细流池**全空**
（只剩法阵/主体/边界/波，全是 essential）。发射器上限按**到相机距离**取最近 N 个 ——
远处减的全是装饰角色。

## 技术债清偿：驱散语义筛选（2026-08-03）

上一轮登记的「自由祝福驱散缺口」。根因不是哪一个技能配错，而是**表达缺失**：
「解除减速和定身」类技能按驱散**类别**永远选不全 —— 减速的 dispelType
天生五花八门（断筋 movement、霜矢 magic、毒刃 poison），定身还是
`applyControl()` 统一标 magic 的**匿名** `control.root` 光环。
于是自由庇佑的 `dispel types:[Movement]` **什么都清不掉**，而单测全绿 ——
测试给的 slowAura 恰好标了 movement。把霜矢改标 movement 也不行：
驱散魔法会反而摘不掉它，单一 dispelType 表达不了「既是魔法又是移动限制」。

### 修法：`dispel` 效果加 `impairs: 'slow' | 'movement'` 语义筛选

按光环**实际做了什么**选（'slow' = `modifiers.moveSpeed < 1`，
'movement' = 减速 ∪ `flags.rooted`），与技能说明的措辞直接对齐。
`dispelType: None`（不可驱散）对两种口径**都依然不可驱散**——语义筛选
不是绕过 None 的后门（潜行自带的 15% 自减速不会被友方驱散意外摘掉）。

三个受害者一并迁上去：

| 技能 | 旧表达 | 新表达 |
|---|---|---|
| 圣骑士·自由庇佑 | `types:[Movement], count:99`（清不掉任何东西）| `impairs:'movement', count:'all'` |
| 猎人·后撤跃 `clearsSlow` | `types:['movement']` | `impairs:'slow'`（**只清减速** —— 被定身时人跳不出去，清定身语义不通）|
| 盗贼·遁形 | `{kind:'custom', handler:'rogue.clearSlowAndRoot'}`（⛔ 只记事件无效果）| `impairs:'movement'` —— **custom 逃生舱 3 → 2 处**，路线图判据「降到 3 处以下」这次是真达成 |

## 技术债清偿：软推开接进移动积分（2026-08-03）

四期登记的三个既有 bug 里最后一个：`separationVelocity()`（13.5「玩家、宠物
和召唤物不形成完全实体堵门」，验收 #43）从 M1 起就在、单测也绿 ——
**零调用方**，角色可以完全重叠站成一个点。

### 修法：`stepMovement` 加 `separation` 输入，三路径同源

- **只进位移不进 `velocity`** —— 推开是外力位移不是动量，混进速度会让
  「被推了一下」在松手后继续滑行（tick 断言钉着「推完不留残余速度」）
- 走步骤 5 的 `moveAndSlide`，**推不进墙**、推不出合法区 —— 与玩家自己的
  移动受同一套碰撞约束，不需要单独的钳制路径（断言：贴墙被推停在墙面+半径处）
- `tickWorld` 第 2 步对**所有**其他存活实体算（站桩假人也占地方）；
  试验场玩家由 `TestbedScene.simulate` 同源计算；预测器经 `opts.others`
  回调取最新快照里其他实体的位置（近似输入，误差只在重叠窗口内且有界 ——
  speedMultiplier 的教训：预测漏算权威侧输入 = 平滑档里的持续橡皮筋）
- ★ 顺带补上 speedMultiplier 那轮的漏接：`Predictor.sample()` 前向预测
  一直没传速度倍率（只有重放传了），减速期间最新一两帧总是超前。
  现在积分选项收口成 `stepOpts()` 一个方法，「只改一处」在结构上写不出来
- tick 级断言过变异测试（把 separation 换成零向量，断言变红）

### 顺带：verify-m8 #48b 的采样竞态（与本轮改动无关的既有问题）

## 特效改造三期：Q 版夸张化（2026-08-03）

用户实测二期后提出：「既然是 Q 版的，技能特效就可以做得夸张一些、酷炫一些，
当然界面交互流畅性要保证」。基调有据可依 —— docs/10 偏差 #6 已把美术基调
定为「可爱卡通（Q 版）」，而当时的参数是照「够用」调的。

**核心判断：夸张 ≠ 把粒子数乘二。** 粒子翻倍最贵、最容易掉帧、观感提升最小。
本轮按性价比取用，前四个维度**零成本**：弹性曲线 > 尺寸对比 > 时间错落 >
颜色分层 > 粒子数量。

| 交付 | 说明 |
|---|---|
| **弹性回弹曲线** | `pop()` 拆成 `popSize`（过冲到 1.2）与 `popAlpha`（封顶 1）。★ 过冲**只能给尺寸**：加法混合下 alpha>1 会被截成平顶，既糊屏又打穿第一人称红线 |
| **技能分量分级** | 新增 `vfx/skillWeight.ts`，`weightOf()` 从 `SkillDef` 推导（冷却主导 0.5）。释放爆发、蓄力法阵、大招爆闪全部乘 `vfxScaleOf()`（0.85~1.5）|
| **贴图 16 → 25 张** | 同一个已登记的 CC0 包（Kenney Particle Pack）。冲击波换成**真空心环**、暴击加星芒（形状通道）、重击加爆炸云、**四张刀光轮流用** |
| **事件池 32 → 40** | 修一个当时就在漏的洞，见下 |
| **fps 挂进自检** | 零新增计算（`GameLoop` 本来就在算）。★ 联网路径此前**完全没有帧率读数**，而 12v12 正是最坏情况所在 |

### 本轮抓到的三个问题（两个是我自己写错的）

1. **弹性曲线第一版白写了**：把过冲写成「在 `sin` 上叠一项」，而 `sin(πt)`
   要到 t=0.5 才够到 1、过冲项却必须在前段衰减掉 —— 两个窗口不重叠，
   实测峰值只有 **1.0095**，肉眼完全看不出来。**而单测是绿的**（峰值确实 >1）。
   教训写进测试：只钉「峰值 >1」不够，必须同时钉「起手足够快」，
   否则这条曲线可以悄悄退化回 `sin`。
2. **分量分级第一版排序是错的**：dump 出 90 个技能后发现 **90 秒冷却的
   神圣壁障排到第 11 位、还不如 20 秒的照明弹**，4 秒引导的冰霜风暴却冲到 0.99。
   根因是 `cast` 权重给到 0.30，而玩家心里的大招（`cooldown ≥ 60` 的 11 个）
   **有 10 个是瞬发**。改成冷却主导后那 11 个全进前 12。
   ★ 这条也说明**必须先 dump 再定阈值**，不能拍脑袋。
3. **事件池当时就在漏**：一发 8 目标 AOE = 8 主爆发 + 8 碎屑 = 16 格活约 0.6 秒，
   0.6 秒内两发正好打满 32 格，第三发开始按「回收最旧」把**上一发还活着的
   粒子**掐掉。与拖尾把自己刷没了是同一种病，只是源头换成了事件池自己。

### 红线（一条既有断言都没改）

细流池 48 格与三条 `ceil(life/cadence)` 预算断言**一格没动** —— 它们有价值

### 三处刻意的实现选择

1. **`validateCast` 是唯一的校验入口**。开始、完成、HUD 图标变灰全走它。
   HUD 自己算一遍迟早会出现「图标是亮的但按下去失败」——最让人困惑的一类 bug。
2. **`applyInterrupt` 不碰冷却**。7.2 规定打断落空也进冷却，把冷却留在调用点上，
   就没法被 `if (命中)` 分支绕过。两个调用点（玩家、假人）都能看到这一句。
3. **`onDamageTaken()` 是个空函数**。验收 #14「普通伤害不打断施法」是一条
   *什么都不做* 的规则 —— 写成可搜索、可被测试引用的空函数，

### 假人 AI 的一个非平凡设计

战士假人的拳击有 **0.45 秒反应延迟**。这不是拟真装饰：反应时间为 0 的 AI 会在
读条开始的同一 tick 打断，人类玩家永远读不完任何条，7.5 的假读条博弈就**不存在**了。
规则实现对了，玩法却没了 —— 这是端到端验收才能发现的问题，单元测试发现不了。

### 三处结构性保证

1. **漏注册效果 = 启动即崩，不是静默无效。** `assertAllEffectsRegistered()` 在

2. **所有位移只有一个出口。** `displacement.ts` 里每个位移处理器都调用同一个

   就必须显式绕开这个模块，代码审查一眼能看到。
3. **`StatusFlags` 由光环派生。** M2 时它是手动赋值的占位实现；M4 换成

   调用点**一行都没改**。这正是当初把它单列成结构的原因。

### 本阶段发现并修掉的四个真 bug

1. **读条技能完全不结算效果。** `beginCast` 传入的 `onCompleted` 只对**瞬发**技能
   生效，读条技能走的是 `tickCasting` 那一路 —— 两个事件出口我只接了一个。
   技能日志显示「完成」，但什么都没发生。已在 `casting.ts` 的 `CastEvents`
   上加了醒目警告，并把完成处理收敛到 `onCastCompleted()` 一处。
2. **假人法师打自己。** 统一完成入口时我从 `targets.hard` 重新取目标，
   但假人从没设过硬目标 → 回退到 `[caster]`。改为使用 `CastState.targetId`：
   施法开始时锁定的是谁，完成时就结算给谁。
3. **战士假人从 14 米外用 3 米技能打断。** 它直接调 `applyInterrupt`，
   绕过了 `validateCast` 的距离校验。改为先过 `validateCast` ——
   假人和玩家受同一套规则约束。
4. **假人永远转不了身。** yaw 恒为 0，玩家站在它背后时拳击被判 `WrongFacing`，
   于是它一次也打断不了。假人现在每 tick 面向玩家。

### 三处「把否定式规则钉死」的做法

规格书里有几条是**否定式**的 ——「不得阻止」「不能通过 X 规避 Y」。
这类规则最容易被后来「顺手加的限制」破坏，因为破坏它不会让任何东西报错。

1. **`compositionHints()` 的 `blocking` 字段类型就写死成 `false`**。
   3.2 允许提示「缺少治疗」但不得阻止准备。想让某条提示变成阻塞条件，
   得先改这个类型 —— 改了会被 `room.test.ts` 拦下。
2. **`canStart()` 完全不看阵容**，只检查「选了职业、点了准备、人数符合规则」。
   测试里有全队同法师、全队无治疗、全队近战三个用例各自断言能开始。
3. **`leaveMatch()` 在比赛中不把玩家移出房间**，只标记断线。
   11.5：「主动退出立即按淘汰处理，不能通过退出规避死亡统计」——
   移出去就没法记他的死亡了。

1. **空场景在第一 tick 就被判平局。** 两队都是 0 存活 → 双方全灭 → 平局。

2. **自定义短回合永远进不了决胜阶段。** `dampeningAt()` 在抑制起始时间之前

### 验收 #34 的实现方式：让函数短到无处藏私

「换装不能刷新普通攻击、取消后摇、重置技能、恢复资源或清除负面」——
五件事都是**不做某事**。破坏它们不会让任何东西报错，只会让某个玩家发现
「切一下武器就能重置冷却」然后再也不用别的打法。

`completeSwap()` 因此只有两行赋值（`weaponId` / `armorId`），其余状态一律不碰。
`loadout.test.ts` 逐项断言这五样东西在换装前后**完全相等**，
`verify-m6.ts` 再在一个「打架打到一半」的完整状态上复验一遍。
想加一行「顺手回点资源」就会同时点亮两处红灯。

同样的手法用在另外两条否定式规则上：

- **`beginPickup()` 的所有失败路径都返回 `itemRemains: true`。**
  10.2 规定「错误交互不会使物品消失」（验收 #29）——
  这个字段存在的唯一意义就是提醒调用方别删。成功路径是**唯一**有
  `store.drops.splice()` 的地方。
- **`enemyLoadoutView()` 的返回类型里根本没有备用装备字段。**
  10.6 / 验收 #36 要求敌人看不到备用装备 —— 网络层照着这个类型序列化
  就不可能泄露。测试直接断言 `Object.keys()` 恒为三项。

### 另外两处「与既有规则同源」的实现

- **10.5：普通伤害不中断拾取**，与 7.3「普通伤害不打断施法」是同一条设计意图。
  `tickPickups()` 的中断条件里刻意没有伤害分支，并写了注释说明这是有意的空白 ——
  和 M2 的 `interrupt.onDamageTaken()` 一样的处理。
- **10.2：「谁先完成拾取谁获得」** 靠对 `endsAt` 排序保证，
  而不是靠 Map 的迭代顺序 —— 后者在服务器与客户端之间不保证一致。

### ★ 验收 #48 是怎么被「钉死」的

14.4 是一条**否定式**规则：「不能隐藏角色、目标、旗手、投射物主体、
地面真实边界、控制状态、完全免疫和复活保护。」

这类规则最容易在「跑一遍看看没问题」之后，被某次为了提帧数的改动悄悄破掉 ——
而且只有把画质调到最低玩一局的人才会发现。所以这里的做法不是靠自觉：

```ts
// 这个函数只接受 DecorativeRole
export const hiddenAtQuality = (role: DecorativeRole, quality: QualityTier): boolean
```

想在低画质隐藏一个关键元素，必须先把它从 `ESSENTIAL_ROLES` 挪到 `DECORATIVE_ROLES` ——
那是一次显眼的、会在 review 里被拦下的改动，而不是在某个 draw 函数里
随手加一行 `if (quality === 'low') return;`。**「低画质隐藏了控制状态」在本项目里是类型错误。**

与 M6 的 `completeSwap()` 短到无处藏私、`enemyLoadoutView()` 返回类型里
根本没有备用装备字段，是同一个思路。

### ★★ 16.4 是怎么被「钉死」的

16.4 第二条是全项目最容易被悄悄破坏的一条否定式规则：
**「不能只按总伤害或击杀数评选最佳玩家。」**

破坏它不会让任何东西报错，只会让治疗和旗手永远拿不到最佳玩家 ——
而且要打完一局、翻到统计页才看得出来。所以做了四层：

1. `bestOverall` 的评分**必须**是 `CompositeScore`，它带一个 `declare const`
   的 unique symbol 品牌字段 —— 手写 `{ value, parts }` 冒充它是**类型错误**，
   唯一构造入口是 `composeScore()`
2. `composeScore()` 在维度少于 4 个时**抛异常**
3. 且任一维度权重占比超过 35% 时**抛异常** —— 光有「维度数 ≥ 4」不够：
   combat 权重 0.97、其余三项各 0.01，形式上是四个维度，实质仍是只按伤害评选
4. 伤害与击杀合并成**同一个** `combat` 维度 —— 拆成两个就能用「两个维度」
   凑够维度数下限，而 16.4 禁止的正是「只按总伤害**或**击杀数」

`verify:m9` 里有一条直接的行为验证：造一个 500 万伤害 50 杀但其余一无所有的
「纯输出」，他**拿不到**最佳综合玩家。

### ★★ 验收 #5 为什么必须做在快照层

「未被发现的潜行目标不能被点击、Tab 或小地图选中」有两种实现方式，只有一种是对的：

- ✗ 把 `stealthed: true` 发给客户端，让客户端别画 —— **改前端就能透视**
- ✓ 未被发现的潜行者对该客户端而言**根本不存在**（docs/08 §4.1 原话）

所以裁剪发生在**构建**快照时。`buildSnapshot(deps, viewer)` 的 viewer 是必填参数，
本文件不导出任何不带 viewer 的变体 —— 「先建一份全量快照再按人过滤」没有入口，
因为全量快照一旦存在，迟早会有人为省一次遍历直接广播出去。

**8.5 与 #5 的冲突**是这里最需要判断的一处：8.5 要求「决胜阶段所有玩家大致位置可见」，
而 #5 禁止潜行者被选中。两条同时成立的方式是让位置走一个**没有实体 id** 的
独立通道（`SuddenDeathBlip`）—— 选中链路（点击 / Tab / 小地图）全都要 id，
于是「决胜阶段能选中潜行者」在结构上不可能发生。位置还量化到 6 米网格：
「大致位置」就该是大致的。

### ★★ `?art=off` 为什么必须存在 —— 一次实测逼出来的

接入美术后第一次跑 `verify:m1` **直接超时**。查下来不是缺陷：
`--use-gl=swiftshader`（M1–M8 验收脚本用的软件渲染）下，
PBR 材质 × IBL × 四个蒙皮角色把帧率从 **27 压到 4**。

那 106 项验收验的是移动、镜头、目标、打断，**没有一条与美术有关**，
却会因为跑不动而集体变红 —— 那是测量环境的伪影，不是代码的问题。

所以加了 `?art=off`，并且它的契约是**精确**回到 M11：
不只是「不加载素材」，还包括把地图材质换回 `MeshLambertMaterial`、
关掉 ACES 色调映射。⚠️ 只做前者时实测是 14 FPS（历史是 21）——
**光是 Lambert→Standard 就吃掉三分之一帧率**，而「能与历史直接对比」
正是这个开关存在的全部理由，差一点就不算数。回到精确 M11 后是 27 FPS。

| 脚本 | 跑在哪条路径 | 验什么 |
|---|---|---|
| `verify:m1`–`m10` | `?art=off` | 规则接线（与 M0–M11 同一条路径）|
| **`verify:m12`** | `?art=on`（默认）| 美术层本身 + #10 / #48 **重验** |

★ docs/13 原话：「这两条都要在 `verify:m12` 里重验，而不是假定 M1/M8 的
结论自动延续。」—— 分工是照着它定的。

### ★ 三条红线的落点（docs/14 §M13）

- **既有 URL 参数原样保留** —— 大厅只在 `?lobby` 分支被动态 import，

### ★★ 架构决定：连接归大厅，场景每场重建

`CharacterView.setClass` 幂等首调生效、`SnapshotCombatView.skills` 首赋后粘住 ——
跨局复用场景的话「回房间换个职业再开」会让模型与技能栏悄悄停在上一局。

MatchEnd 回房间时整体销毁 —— 上一局的状态**从根上不存在**，不是逐字段去清。

#### ⚠️ 上表原本过于乐观 —— M11 核查后的修正

★★ **被迁走的那 4 条，此前从来没有生效过。** `custom` 兜底实现「只记事件、

于是「减速逐渐恢复」「速度下限 80%」「审判易伤」「受益者掉旗」四条规则
写在数据里、写在技能描述里，却四个阶段一次都没发生过 —— 而单测与九支验收
全绿，因为**从来没有人测过它们**。迁移时补了 `data/migrations.test.ts`。

剩下 4 条**不是数据编辑能解决的**，路线图「降到 3 处以下」这条判据**不可达**：

- ★★ **`SkillDef.requires` / `ConditionDef` 是死 schema —— 全仓零个读取方。**
  `validateCast()` 从不读它，也不存在 `canCast()`。把 `requires` 写进数据会得到
  **静默被忽略的配置**，比现在**更糟**：连 custom 那条兜底事件都没了。
- `outOfCombat` 没有数据源：`CombatEntity` 上没有 `inCombat` / `lastDamageAt`。
- `recentlyParried`：**招架从未被掷判过**。`combat.ts` 里没有任何闪避/招架判定，
  `parry` 只是个聚合数字。没有招架事件，就谈不上「最近招架过」。
- ~~`rogue.clearSlowAndRoot` 的方案**有误**：定身被 `applyControl()` 标成
  `dispelType: 'magic'` 而非 `'movement'`，movement 型驱散点不到它。
  ⚠️ 同一个 bug 已经随 `leapBackward.clearsSlow` 发出去了。~~
  ✅ **技术债清偿批已解决**：`dispel` 效果加了 `impairs: 'slow' | 'movement'`
  语义筛选（按「光环做了什么」选，不按驱散类别），消失/自由庇佑/后撤跃三处
  全部迁上去，见「技术债清偿：驱散语义筛选」。
- `druid.prowl` 语义不符：`requires` 是**施法时**的门禁，而 prowl 需要的是
  形态期间的**持续监视**（脱战即获得潜行）。

**三件前置里已完成两件**：
· ✅ **战斗状态追踪** —— `CombatEntity.lastCombatAt`，由 `dealDamage()` 双向打标
  （★ 攻击者也进战斗，否则「打完就潜行」的偷袭完全不受限制）
· ✅ **`requires` 的读取** —— `validateCast()` 现在真的读它，死 schema 复活
· ✅ **闪避/招架/格挡** —— `combat.ts` 的 `rollAvoidance()`，`lastParryAt`
  为 `recentlyParried` 提供数据源。
  ★★ **随机源做成「按实体分流的种子 PRNG」**，不是全局单流：
     全局单流的问题不是空间（就一个 32 位整数），是**顺序耦合** ——
     每次掷骰推进同一份共享状态，于是「谁先掷」决定所有后续结果。
     后果很实际：加一处随机判定会改变整局走向；等价重构调换结算顺序
     会让回放与配平复现全部失效。按实体分流后 A 的掷骰不影响 B，
     代价是每实体多 4 字节（12v12 共 96 字节）。
  ⚠️ `rng` **不进快照** —— 它是服务器内部状态，发出去等于让人预测下一次闪避。

> （`death_grip` / `psychic_scream` / `mortal_strike` / `kidney_shot`…），
> 而它们是**承重的**：光环 id、`vfx` key、`WeaponDef.grantsSkills` / `removesSkills`、
> `skillModifiers` 的记录键全都引用它们。18.3 说的是「技能名称」——
> 如果 id 与 vfx key 也算，这就不是一次字段替换，而是一次跨数据层的重命名。
>
> ★ 这一项需要**创作决定**（起什么名、什么风格基调），不适合自动生成。
详见 [09-asset-license.md](09-asset-license.md) §3。

### 8. 近战 inRange 把碰撞体重叠判为「超出距离」（M15 发现）

`math/geometry.ts` 的 `edgeDistance` 注释明说「返回值可能为负（碰撞体重叠），
**调用方按 <= max 判断即可**」—— 但 `inRange()` 统一入口对近战距离同时检查
`d >= minRange`，而 minRange 默认 0：**双方碰撞体一重叠（边距为负），
min=0 的近战技能反而 OutOfRange**。

复现：站进战士假人模型里（中心距 < 1.0 米）读条 —— 它的拳击永远不起意
（M15 验收脚本的面包屑抓到的：`dist=0.55`、连续 12 个饵零打断）。
试验场没有实体碰撞，真人玩家完全可以走进假人身体里撞上这个死区。

**改法向**：近战分支的 min 检查只对 `minRange > 0` 的技能生效（冲锋这类
「太近不能用」语义不受影响），或把负边距钳到 0 再比较。改动在 sim 层 ——
M15 红线（不动 sim 一行）之内不修，**动手前记得补「重叠时可施放」的单测**
（6.2 的边缘语义此前没有负值用例）。优先级：低（需要主动钻进模型里才触发）。
